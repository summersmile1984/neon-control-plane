## 1. 技术选型与工程约定 `[D]`

| 项 | 选择 | 理由 |
|---|---|---|
| 运行时 | Node 22 LTS，ESM，TypeScript 5.8 `strict` | 与 SiteOps 一致，团队熟 |
| HTTP | Hono 4 | 与 SiteOps 各 Worker 同框架，路由/中间件写法一致 |
| 校验 | `ajv` + `ajv-formats`，schema 直接取自 `spec/neon-api-v2.json` | 不手写 schema，杜绝与官方漂移 |
| 存储 | `better-sqlite3`（WAL，同步 API） | 单进程控制面，事务简单；避免异步锁 |
| 容器 | Docker Engine API over unix socket，`undici` 直接发 HTTP | 不引入 dockerode，减少依赖面 |
| 日志 | 结构化 JSON 到 stdout（`level/msg/request_id/operation_id`） | 与 SiteOps observability 口径一致 |
| 测试 | vitest：`unit` / `contract` / `e2e` 三层 | 与 SiteOps 一致 |
| Lint | eslint flat config，与 SiteOps 同规则集 | |
| 包管理 | pnpm | |

**代码硬约定**（评审卡这几条）：
1. **任何响应体必须由 `respond(c, schemaName, payload)` 出口**，该函数在非生产环境用 ajv 校验后再返回；校验失败抛 500 并打日志。杜绝"字段拼错但测试恰好没断言"。
2. **任何写操作必须先落 `operations` 行再触发副作用**，副作用函数必须幂等（以 `operation_id + step` 为幂等键）。
3. **口令明文只在三处出现**：生成时的内存变量、`roles.password_ciphertext`（AES-GCM）、`reveal_password`/create 响应。禁止进日志、禁止进 operations 表。
4. **对外 ID 与内部 ID 分离**：`projects.id`（对外 `adj-noun-123456`）↔ `projects.tenant_id`（pageserver 16 字节 hex）；`branches.id`（`br-…`）↔ `branches.timeline_id`。任何 adapter 只收内部 ID。
5. **adapter 不认识业务**：`pageserver.ts` / `compute.ts` / `docker.ts` 只做协议翻译与错误归类，不读数据库。

### 4.3 错误映射（`http/errors.ts`）`[D]`

统一抛 `ApiError { httpStatus, code: ErrorCode, message, requestId }`，序列化成 spec 的 `GeneralError{ code, message, request_id }` `[F]`。

| 场景 | HTTP | code |
|---|---|---|
| API key 缺失/错误 | 401 | `AUTH_FAILED` |
| 路径对象不存在 | 404 | `RESOURCE_NOT_FOUND`（project/branch/endpoint 分别用 `PROJECTS_NOT_FOUND` 等，取 spec `ErrorCode` 里存在的值，M0 从 spec 里核对可用取值清单） |
| 请求体不合 schema | 400 | `BAD_REQUEST` |
| 名称重复（branch/database/role） | 409 | `ALREADY_EXISTS` |
| 分支上已有 read_write endpoint | 409 | `ALREADY_EXISTS` |
| `parent_timestamp` 超出保留窗口 | 400 | `WRONG_LSN_OR_TIMESTAMP` |
| `reveal_password` 但 `store_passwords=false` | 412 | `PRECONDITION_FAILED` |
| 有正在跑的同资源 operation | 423 | `LOCKED`（`RunningOperations` 语义，proxy 侧视为可重试） |
| 后端（pageserver/docker/compute）失败 | 500 | `INTERNAL_SERVER_ERROR` |

**已核实（2026-09-07）**：`spec.components.schemas.ErrorCode` 是 `{"type":"string","default":""}`，**没有枚举**，官方文档也未公布取值表。因此上表右列由我们自定；实现落在 `src/http/errors.ts` 的 `ERROR_CODES`，`tests/contract/spec-subset.test.ts` 有一条断言守住"spec 仍未给出枚举"这一前提——哪天官方补了枚举，这条测试会红，届时改用官方取值。与 proxy 交互相关的两类保持 proxy `Reason` 的语义：`RUNNING_OPERATIONS`（可重试）、`*_NOT_FOUND`（不可重试）。

## 5. 关键流程的代码级设计

### 5.1 `POST /projects` `[D]`

```
1. 校验 body（ProjectCreateRequest）
2. tenant_id = randomHex(16); project.id = slug()
3. pageserver.locationConfig(tenant_id, { mode:'AttachedSingle', generation:1, tenant_conf:{ pitr_interval: `${history_retention_seconds}s` } })
4. timeline_id = randomHex(16); branch.id = 'br-'+slug()
   pageserver.createTimeline(tenant_id, { new_timeline_id, pg_version })
5. 事务写 projects / branches(main, is_default=1) / roles(neondb_owner) / databases(neondb)
6. 入队 operations: create_timeline(finished，已同步做完) + start_compute（若请求没禁用默认 endpoint）
7. 返回合体响应；connection_uris 由 §6 组装
```

同步做 pageserver 调用、异步做 compute 启动，是为了让 `POST /projects` 立刻返回可用的 branch，同时把慢的容器启动放进 operation——与云端行为一致（云端 `POST /projects` 也返回 `operations[]`）。

### 5.2 `POST /branches` + PITR `[D]`

```
1. parent = body.branch.parent_id ?? project.default_branch_id
2. ancestor_start_lsn:
   - body.branch.parent_lsn 直接用
   - body.branch.parent_timestamp → pageserver.getLsnByTimestamp(tenant, parentTimeline, ts)
     · 越界判定不依赖 kind（实测新 timeline 恒为 nodata，越界也不抛错）：改为比较 lsn < min_readable_lsn → 400 WRONG_LSN_OR_TIMESTAMP
   - 都没有 → 省略（pageserver 取父 timeline 末端）
3. pageserver.createTimeline(tenant, { new_timeline_id, ancestor_timeline_id, ancestor_start_lsn, pg_version })
4. 写 branches 行；body.endpoints[] 里每项 → 建 endpoint 行 + start_compute operation
5. 201 合体响应
```

### 5.3 角色与库的生效路径 `[D]`

**核心约束**：Postgres 里的角色/库最终由 compute 的 spec 决定。控制面写库后必须把 spec 重新下发。

```
createRole(branch, name):
  password = randomPassword(); scram = scramSha256(password)
  tx: insert roles(branch,name,ciphertext,scram)
  operation apply_config(branch) → reconciler:
     endpoints = 该 branch 的 active endpoints
     for ep: spec = buildSpec(branch); compute.configure(ep, spec)
  响应立刻返回明文（不等 operation 完成，云端同样如此）

deleteRole(branch, name):
  tx: delete roles 行
  operation apply_config(branch, delta_operations=[{action:'delete_role', name}])   [F]

resetPassword: 同 createRole，但 update 现有行

createDatabase(branch, name, owner):
  tx: insert databases
  operation apply_config(branch)
deleteDatabase: delta_operations=[{action:'delete_db', name}]
```

`[?]` M0/M1 必测：spec 里删掉一个 role 而不给 `delta_operations`，compute_ctl 是否自动 DROP。若否，则删除路径**必须**依赖 `delta_operations`（本文按"必须"实现，实测若能自动则保留 delta 也无害）。

### 5.4 Endpoint 生命周期 `[D]`

状态机（`endpoints.current_state`，取值对齐 spec 的 `EndpointState: init|active|idle` `[F]`）：

```
          create                start_compute ok
 (none) ─────────► init ──────────────────────────► active
                    │                                 │  │
                    │ start 失败                       │  │ suspend / 空闲超时
                    ▼                                 │  ▼
                  init(retry)                         │ idle
                                                      │  │ start / wake_compute
                                                      │  ▼
                                                      └ active
 delete: active|idle ──► (terminate + rm) ──► 行 deleted_at
```

`start_compute` step 序列（每步幂等，写 `cursor_step`）：

| # | step | 幂等键 | 失败处理 |
|---|---|---|---|
| 1 | `ensure_spec_file` 生成 spec 写入卷 | 文件内容 hash | 重写 |
| 2 | `ensure_container` Docker create（name = endpoint id） | 容器名存在即复用 | 409 视为成功 |
| 3 | `start_container` | 已 running 视为成功 | |
| 4 | `await_ready` 轮询 compute `GET /status` 到 `running`，超时 90s | 直接重查 | 超时 → operation failed，容器保留供诊断 |
| 5 | `mark_active` 更新行 | | |

`suspend_compute`：`POST /terminate?mode=fast` → 等容器退出 → `docker stop` → `current_state='idle'`、`suspended_at`。

### 5.5 Reconciler（`reconciler/loop.ts`）`[D]`

```ts
export interface OperationStep {
  readonly name: string;
  run(ctx: StepContext): Promise<void>;   // 必须幂等
}
export interface ActionDefinition { readonly action: OperationAction; steps(payload): OperationStep[]; }

// loop：每 250ms 一轮（可配）
// 1) SELECT * FROM operations WHERE status='scheduling' AND (retry_at IS NULL OR retry_at<=now) ORDER BY created_at LIMIT 1
// 2) CAS → running，started_at
// 3) 从 cursor_step 起逐步执行；每步成功后 cursor_step+1（单独事务）
// 4) 全部完成 → finished + total_duration_ms
// 5) 抛错 → failures_count+1；<5 次：status='scheduling'、retry_at=now+backoff(2^n s, cap 60s)；≥5：status='failed' + error
// 6) 同一 (project_id, branch_id|endpoint_id) 同时只跑一个 operation（内存锁 + DB 查询双保险）
```

`error` 字段只写归类后的短语，不写后端原始报文（避免泄露连接串）。

## 6. 连接串组装（`domain/connection-uri.ts`）`[D]`


| mode | host | port | 查询串 |
|---|---|---|---|
| `direct` | `127.0.0.1` | `endpoint.pg_port` | `sslmode=disable` |
| `sni-router` | `${endpoint.id}--compute--55433.${zone}` `[F]` SNI 形状 `svc--ns--port` | 省略 | `sslmode=require&channel_binding=require` |

```ts
export interface SpecBuildInput {
  project: ProjectRow; branch: BranchRow; endpoint: EndpointRow;
  roles: RoleRow[]; databases: DatabaseRow[];
  storage: { pageserverConnstring: string; safekeeperConnstrings: string[] };
  deltaOperations?: Array<{ action: 'delete_role'|'delete_db'|'rename_role'|'rename_db'; name: string; new_name?: string }>;
  operationUuid: string;
}
export function buildComputeSpec(input: SpecBuildInput): ComputeSpecEnvelope;
```

规则：
1. `cluster.roles` 恒含 `cloud_admin`（超级用户，compute_ctl 自己连本机要用）+ 每个业务 role（`encrypted_password` = SCRAM verifier；`options` 按 `no_login` 给 `NOLOGIN`）。
2. `cluster.databases` = 业务库；`owner` 必须是 roles 里存在的名字，否则抛错（守住 compute 启动失败这一类问题）。
3. `mode` = endpoint.type === 'read_write' ? `'Primary'` : `'Replica'` `[F]`。
4. `suspend_timeout_seconds` 取 endpoint 值（`-1` = 不挂起 `[F]`）。
5. `settings` 以官方 23 条为基线（`spec/compute-settings.base.json` vendored），叠加 project/endpoint 的 `pg_settings`，冲突以后者为准；`port` 恒 55433。

## 10. proxy 内部 API（`http/routes/cplane.ts`，M3）`[F]` 字段来自 proxy 源码

```
GET  /cplane/get_endpoint_access_control?session_id&application_name&endpointish&role
     → { role_secret, allowed_ips[], allowed_vpc_endpoint_ids[], block_public_connections, block_vpc_connections, project_id, account_id, rate_limits }
GET  /cplane/wake_compute?session_id&application_name&endpointish

```
鉴权：`Authorization: Bearer $NEON_PROXY_TO_CONTROLPLANE_TOKEN`；`X-Request-ID` 透传。`wake_compute` 命中 `idle` endpoint 时同步触发 `start_compute` 并等待就绪（最长 30s），超时返回可重试错误（`ControlPlaneErrorMessage` 的 `RunningOperations` 语义 `[F]`）。

### 10.1 接真 proxy 测出的四条硬合同 `[F]`（build 8464，2026-09-07）

上面的字段是照 proxy 源码写的，但真接上去还是踩了四个坑。共同点是**给错了 proxy 只报模糊错误**，真实原因全在它自己的日志里：

| # | 事实 | 给错时的现象 |
|---|---|---|
| 1 | `--auth-endpoint` **结尾不能带斜杠**：proxy 自己用斜杠拼方法名 | 请求变成 `/cplane//get_endpoint_access_control`，控制面 404 |
| 2 | 错误体必须是 `ControlPlaneErrorMessage { error, http_status_code, status? }`，**不是** v2 的 `GeneralError { code, message }` | proxy 记 ``failed to parse error body: missing field `error` ``，对客户端报 `reason unclear (malformed error message)` |
| 3 | `cold_start_info` 枚举是 `unknown / warm / pool_hit / pool_miss / http_pool_hit / warm_cached`，**没有 `cold`** | 整个 wake_compute 响应反序列化失败（``unknown variant `cold` ``），客户端只看到 `Control plane request failed` |
| 4 | 不要开 `--is-private-access-proxy=true` | 每个会话都被要求带 VPC endpoint id，本地客户端一律被拒 |

因此实现上：`/cplane` 前缀下的处理器异常、`onError` 与 `notFound` **统一**用第 2 条的信封（`cplaneErrorBody`）；从零起 compute 上报 `pool_miss`；路由同时注册 `/cplane/x` 与 `/cplane//x`，让第 1 条的错配降级成能用而不是不透明的 404。

`wake_compute` 在请求线程里主动 `reconciler.drain()`，不等后台 tick——proxy 正阻塞在这个 HTTP 调用上，而客户端阻塞在 proxy 上。`claimNext` 是 CAS，与后台循环并发安全。

**风险控制**：这两个路由的响应体单独有金标准 fixture，proxy 版本升级时先跑 `tests/contract/cplane-shape.test.ts`（10 用例，把上面四条都钉住了）。

| # | 本文原写 | 实际落地 | 原因 |

| 1 | `store/repo/{projects,branches,…}.ts` 七个文件 | 一个 `src/store/repo.ts` | 接口面很小，七个文件是噪声；`src/store/rows.ts` 单独放行类型 |

## 16. 本地运维 console `[D]`（2026-09-07 新增）

**为什么需要**：API 完整不等于栈可观测。本地这套东西有 5 个以上容器、异步 operation、以及会互相偏离的两份状态（SQLite 里的 endpoint 行，和 Docker 里的容器）。在 console 之前，回答"现在到底什么在跑、哪一步失败了、连接串是什么"要同时 curl 三四个接口、跑 `docker ps`、再翻 `pnpm dev` 的日志。

**边界**：它是开发工具，不是产品界面，也不属于 Neon 合同，所以**挂在 `/api/v2` 之外**，不过 OpenAPI 校验，也不允许任何客户端依赖。它和 SiteOps Console 不是一回事：那个是租户面的产品，这个只管本地这台机器上的 Neon 栈。

```
GET /              → 页面
GET /console       → 同一个页面
GET /console/state → 一次性聚合快照（与 /api/v2 同一把 API key）
```

**只读**。页面上的每个动作都打真正的 `/api/v2` 路由（建项目、start/suspend/restart、删项目、取连接串），因此 console 走的是和 `provider-neon`、`neonctl` 完全相同的合同，不存在一条会和它们漂移的私有后门。

**唯一新增的能力是 v2 API 给不出来的那一件事：漂移检测。** 需要同时看两份状态才能判断，所以 `createApp` 多收了两个**只读**依赖（`docker`、`pageserver`），仅供这个快照使用，API 本身一行都没碰。

| `drift` 码 | 含义 | 通常原因 |
|---|---|---|
| `container_missing` | 行是 `active`，容器没了 | 有人手工 `docker rm`，或 `start_compute` 在标记之后失败 |
| `container_stopped` | 行是 `active`，容器是停的 | 容器自己退出了 |
| `still_running` | 行是 `idle`，容器还在跑 | 挂起没走完 |

docker 不可达时容器状态是 `unknown` 且**不报漂移**——连不上 docker 不构成"有问题"的证据。

**两条硬约束，测试逐条钉住**（`tests/contract/console-state.test.ts`，8 用例）：

1. **快照里不能有口令**。它要遍历栈里每一个 role，一个粗心的字段就等于把整机的口令发给任何能打开页面的人。只回 `has_stored_password` 布尔值；口令仍然只能经 v2 的 `reveal_password`、对单个 role 显式索取。
2. **页面不能引用 CDN**。本地开发工具必须在断网时可用，所以单文件、无构建、无外部资源。

**两个实现上的决定，都是被真实故障逼出来的**：

- **容器状态不缓存**。原先加了 2 秒缓存，结果快照在每次 start/suspend 之后会说 2 秒假话——而那恰好是有人盯着看的时刻。轮询间隔本来就限制了调用频率，缓存省不下什么，却给一个诊断工具引入了说谎的可能。
- **内容没变就不重绘**。页面每 3 秒轮询一次；无条件重建 DOM 会让按钮在鼠标底下换掉，展开的连接串每 3 秒消失一次，操作流的滚动位置被重置。改成比对签名后跳过，并且在连接串展开期间完全不重绘。
